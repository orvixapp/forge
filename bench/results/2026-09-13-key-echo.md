# 2026-09-13 — Apuesta B: latencia tecla→eco a través de `forge-termd`

`cargo run --release -p forge-bench -- key_echo --iterations 500 --check`

Mide, en el mismo proceso, desde que se escribe `ClientMessage::Key` en el
socket hasta que llega el `ScreenPatch` cuya celda contiene el carácter:
socket Unix → daemon → codificación de la tecla con libghostty-vt → PTY →
eco del kernel (`cat` como programa) → lectura del PTY → parser de Ghostty →
snapshot del render state → socket. Se descartan 5 iteraciones de
calentamiento; entre teclas se envía Backspace para que cada patch sea
distinto.

## Lectura

- El daemon separado no añade latencia perceptible: todo el camino cabe en
  0,2 ms, unas 40 veces por debajo del presupuesto. La apuesta B pasa en
  esta máquina sin necesidad del modo in-process (`terminal.in_process`).
- Lo que un usuario percibe se compone de esto más el tiempo del programa
  (la shell con p10k tarda milisegundos en redibujar el prompt) y el frame
  de la GUI (~1 ms de draw+present, ver `2026-09-13-grid-full.md`).
- Pendiente de la apuesta B: `vtebench` frente a Alacritty, reattach tras
  `kill -9` recuperando 10k líneas, y RSS de `termd` con 50 terminales.
