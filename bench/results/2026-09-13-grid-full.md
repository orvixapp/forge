# 2026-09-13 — Apuesta A: grid 200×60 sucio completo en GPUI

Spike del renderer de grid (ARCHITECTURE.md §31, día 3–5). Compara el árbol
de `div`s por celda/run con un elemento GPUI de pintura directa
(`crates/forge-gui/src/grid_element.rs`).

## Máquina

Portátil AMD Ryzen 3 5300U (4c/8t) · 14 GiB RAM · GPU integrada Radeon
(RADV Renoir, Mesa 26.0.8, Vulkan 1.4) · Linux 7.0.0-31 · KDE Plasma 6.6.6
en Wayland · pantalla interna 1366×768 @ 60 Hz · fuente `monospace` →
DejaVu Sans Mono · gobernador `powersave` (no fijo; ver §5.2: los números
son orientativos hasta registrar la máquina en `MACHINES.md`).

## Cómo se mide

`cargo run --release -p forge-bench -- grid_full --iterations 120 --check`.

Cada muestra cubre **aplicar el patch (12 000 celdas) → render → layout →
paint → `present()`**. El patch se aplica al inicio del tick de frame
(`on_next_frame`) y la muestra se cierra con `cx.defer`, que GPUI ejecuta
justo después de `present()`; así no se cuenta la espera al siguiente
frame del compositor. El JSON incluye `painted_cells` para demostrar que
las 12 000 celdas están dentro del recorte (la ventana usa celdas 6×10 px,
fuente 8 px, para que 200×60 quepa en 1366×768).

Cada frame cambia el glifo (ASCII imprimible rotativo) y el color de
**todas** las celdas, y mueve un cursor de bloque: nada es reutilizable
entre frames.

> La versión anterior del benchmark medía desde el patch hasta el
> `on_next_frame` siguiente, que en GPUI se ejecuta **antes** del draw del
> estado nuevo. Por eso reportaba 6 ms para un árbol de divs que en realidad
> tardaba >200 ms por frame (`ZED_MEASUREMENTS=1` imprime el `draw+present`
> real de GPUI y sirve de contraste).

## Resultados

| Implementación | mediana | p95 | p99 | PSS | Umbral p95 ≤ 4 ms |
|---|---|---|---|---|---|
| Divs por run (commit `ca605da`), draw+present según GPUI | 220 ms | 323 ms | — | 210 MiB | ✗ (80×) |
| Elemento de pintura directa, 12 000 glifos, 240 frames | 3,5 ms | 4,7 ms | 5,3 ms | 41 MiB | ✗ (+0,7 ms) |
| Ídem con el 50 % de celdas en blanco (6 000 glifos) | 2,9 ms | 3,7 ms | — | 38 MiB | ✓ |

Los dos primeros frames de cada serie son calentamiento (rasterizar 94
glifos nuevos y subirlos al atlas: 13 ms y 6 ms) y quedan dentro de las
muestras.

Escenarios vecinos, mismo binario: `idle` 0 frames en 60 s (✓);
`startup_empty` 147 ms mediana / 172 ms p95 (✗ contra 100 ms, pero era
148 / 161–178 ms antes de este cambio: no es regresión del renderer).

## Dónde se va el tiempo (frame de 12 000 glifos, ~4,7 ms según GPUI)

| Fase | Coste | Quién |
|---|---|---|
| `Window::paint_glyph` × 12 000 (dos lookups con lock por glifo + inserción en la escena) | ≈ 2,6 ms (≈ 215 ns/glifo) | GPUI |
| `Scene::finish` + codificación blade + `present` | ≈ 1,1 ms | GPUI |
| Recorrido de celdas, caché de glifos, agrupación por rango, colores | ≈ 0,8 ms | forge-gui |
| `apply_patch` (mueve las filas, no las clona) | ≈ 0,15 ms | forge-gui |

Optimizaciones que sí dependieron de nosotros y su efecto:

- Un quad por *run* de fondo y un sprite por glifo dentro de una sola capa
  (`paint_layer`) en vez de un elemento retenido por celda: 220 → 4,5 ms.
- Emitir los glifos agrupados por grafema, cada grupo en su propia capa:
  el `sort_by_key((order, tile_id))` que GPUI hace sobre los 12 000
  sprites pasa de O(n log n) sobre entrada aleatoria a un barrido lineal:
  6,0 → 5,1 ms.
- Mover las filas del patch en vez de clonarlas y memorizar RGB→HSLA:
  ≈ 0,7 ms menos.

El coste restante escala linealmente con los glifos pintados
(≈ 0,42 ms por cada 1 000) sobre ≈ 0,6 ms fijos.

## Lectura para la decisión

- GPUI **sí** sirve para un grid de texto: el custom element evita miles
  de elementos retenidos, no copia memoria por frame (lee el grid en
  sitio) y deja el proceso en 41 MiB.
- El criterio "p95 ≤ 4 ms con grid sucio completo" se cumple con la
  mediana (3,5 ms) y se queda a 0,7 ms en el p95 en esta máquina de 4
  núcleos con gobernador dinámico. El suelo es la API pública de GPUI
  (`paint_glyph` por glifo); bajar de ahí exige una de estas vías, en
  orden de coste:
  1. Repetir la medida en R1/R2 con gobernador fijo (§5.2) antes de
     decidir; 4 ms es un objetivo de 144 Hz y la máquina R3 no es la
     referencia.
  2. Un `paint_glyphs(&[…])` por lotes en GPUI (parche mantenido sobre
     `gpui 0.2.2`, ≈ 1 ms de ahorro estimado).
  3. Atlas propio + un sprite por fila (`forge-text` contra wgpu o
     `paint_image`), que es el camino del fallback de la §8.2.
- Para la terminal real el siguiente paso es el redibujado incremental:
  filas sin cambios como vistas cacheadas (`AnyView::cached`) que GPUI
  reproduce desde la escena anterior, de modo que un frame típico solo
  pague las filas dañadas.

## Reproducir

```bash
cargo build --release --workspace
cargo run --release -p forge-bench -- grid_full --iterations 120 --check
ZED_MEASUREMENTS=1 target/release/forge-gui --benchmark-grid-frames 120 2>&1 >/dev/null | grep "frame duration"
```
